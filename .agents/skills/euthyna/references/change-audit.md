# 阶段 B：变更面审计

> 审一次变更（PR / commit / diff），回答一个问题：**这次改动有没有让系统变弱？**
>
> 前置：`../SKILL.md` 的三条不可跳过规则。

---

## B.0 先建立基线

**这是第一动作，不是准备工作。** 没有基线，后面所有判断都只能靠感觉。

在**变更前**的版本上，把它们记下来：

| 要记的 | 为什么 |
|---|---|
| 系统级不变量 | 「什么必须永远为真」——不知道就没法判断这次有没有破坏它 |
| 信任边界与权限级 | 哪些数据可信、哪些不可信；代码以什么身份运行 |
| 既有的校验模式 | 这个代码库惯用的校验长什么样，在哪里做 |
| 关键函数的调用关系 | 改动的影响半径靠它判断 |
| 状态流 | 数据从哪来、经过什么、到哪去 |
| **代码本应做什么** | 不是它现在做什么——是它的设计意图 |

漏掉最后一项，就会把「实现与设计不符」误判成「实现有 bug」，或者反过来。

---

## B.1 分清两件事：分析深度 vs 风险等级

这两件事经常被混为一谈，混了就必然出错。

**分析深度**由**改动规模**决定——它只决定你花多少力气：

| 改动规模 | 策略 | 做法 |
|---|---|---|
| < 20 个文件 | 深读 | 读完全部相关代码，全量 blame |
| 20–200 | 聚焦 | 只追一跳依赖，优先高风险文件 |
| 200+ | 外科 | 只做关键路径 |

**风险等级**由**改了什么**决定——它跟规模**无关**：

| 级别 | 触发条件 |
|---|---|
| 高 | 认证、加密、外部调用、资金流转、**任何校验被删除** |
| 中 | 业务逻辑、状态变更、新增公开接口 |
| 低 | 注释、测试、界面、日志 |

> **一行改动可以是最高风险，两千行可以是零风险。** 按规模判断风险是最常见的偷懒。

---

## B.2 逐文件读两个版本

对每个变更文件，不要只看 diff。**把改动前后的版本并排读**，然后逐段回答四个问题：

| 问题 | 要说什么 |
|---|---|
| 改之前是什么 | 原逻辑 |
| 改之后是什么 | 新逻辑 |
| **改动做了什么** | 一句话概括意图 |
| **安全上意味着什么** | 攻击面变大还是变小？校验变强还是变弱？ |

diff 只显示「哪些行变了」，不显示「行为怎么变了」。删掉一行可能什么都没删（比如那行本来就是死代码），
加一行可能把整个执行顺序改了。

### 被删掉的代码要额外查来源

**这是本阶段最容易被跳过、也最有价值的一步。**

对每一段被删的代码，用本项目的产出器查它的来源：

```powershell
node <euthyna 仓库>/bin/euthyna.js history --base <改前版本> --repo <被审计的仓库>
```

⚠️ **不能写成 `node bin/euthyna.js`**——审计时当前目录是**被审计的项目**，不是 euthyna 仓库，
相对路径会报 `Cannot find module`。`--repo` 指的是**被审计的仓库**，`--base` 相对它解析。

它会告诉你：这段被删的代码是哪个提交引入的、那个提交的信息里有没有安全关键词。
**从 `fix` / `CVE` / `security` 提交里删掉的代码，风险默认拉到最高**，除非能证明它是多余的。

不要自己跑 `git blame` 再肉眼读提交信息——那正是本产出器存在的原因，
机器判定同一个 diff 跑两次结果一致，人读两次可能不一致。

读输出时注意「⚠ 未评估的判据」一节：它非空时，这次运行**不能**读成「查过了没问题」。
退出码 `2` 表示完全无法测量，**不得当作干净**。命令与退出码详见 `fact-producers.md`。

### 三条红线

| 现象 | 默认处理 |
|---|---|
| 被删的代码来自安全修复提交 | 按**最高**风险处理，除非证明它已无必要 |
| 校验被删除且没有等价替代 | 按**最高**风险处理 |
| 代码曾经被加进来 → 因安全原因移除 → **现在又被加回来** | 按**回归**处理 |

第三条用产出器可以机械检出：

```powershell
node <euthyna 仓库>/bin/euthyna.js history --base <改前版本> --pickaxe --repo <被审计的仓库>
```

## B.3 测试覆盖：缺口要升级风险，不是记录一下

**没有测试不是「顺便提一句」的事，它是风险升级的理由。**

| 情况 | 处理 |
|---|---|
| 新增函数且无测试 | 中风险升**高** |
| 修改了校验且测试没跟着变 | **高风险** |
| 复杂逻辑（> 20 行）且无测试 | **高风险** |

想说出「已覆盖」，必须拿真实执行证据，不能靠「这个文件有测试文件」推断：

```powershell
node <euthyna 仓库>/bin/euthyna.js coverage --coverage <覆盖率文件绝对路径> --symbol <被改的函数>
```

没有覆盖率文件时：**要么用项目自己的方式跑一次测试产出它，要么把该判据标为「不可评估」**——
`coverage` 会以退出码 `2` 明确告诉你「没能测量」，那不是「没被覆盖」。

> ⚠️ 这个产出器**只能证伪，不能证实**。它说「没被调用过」是可信的；
> 它说「被调用了 N 次」**不能**推出「相关调用点被执行过」。
> 详见 `fact-contract.md`。

## B.4 爆炸半径

统计每个被修改的函数有多少调用方：

| 调用方数量 | 等级 |
|---|---|
| 1–5 | 低 |
| 6–20 | 中 |
| 21–50 | 高 |
| 50+ | 极高 |

**优先级由「风险 × 半径」共同决定**：

| | 半径极高 | 半径高/中 | 半径低 |
|---|---|---|---|
| **风险高** | P0——深度分析 + 全部依赖 | P1 | P2 |
| 风险中/低 | P1 | P2 | P3 |

数字要由工具产出，不要目测。可选的上游产出器见 `../SKILL.md` 的生态分工一节。

## B.5 高风险变更要做对抗建模

对每个高风险改动，回答：

**1. 攻击者是谁**

| 维度 | 取值 |
|---|---|
| WHO | 未认证外部用户 / 已认证普通用户 / 恶意管理员 / 被攻陷的依赖 / 抢跑者 |
| WHAT | 只能用公开接口 / 需要已认证角色 / 需要特定权限 |
| WHERE | 具体端点或函数 |

**2. 攻击路径**：入口点 → 具体调用与参数 → 如何到达脆弱代码 → 代码里发生了什么 → 达成什么。
**必须给出可达性证明**：那个函数确实是公开可达的、攻击者确实有这个权限、路径确实经过真实接口。

**3. 可利用性三档**

| 档 | 条件 |
|---|---|
| 易 | 公开接口、无需特殊权限、单次调用 |
| 中 | 需要特定条件或提升的权限、多步骤 |
| 难 | 需要特权或罕见条件、需要大量资源 |

**4. 完整利用场景**：起始位置 → 逐步（命令与参数 / 为什么有效 / 系统状态如何变化）→ **具体可测的影响**。

> 影响**禁止**写「可能导致问题」。必须落到确切的数据、具体的权限、确切的量。
> 写不出来，通常说明你还没追到影响。

**5. 与基线交叉比对**

- 是否违反了 B.0 记下的系统级不变量？
- 是否跨越或破坏了信任边界？
- 是否绕过了这个代码库惯用的校验模式？
- 是否是此前已修复问题的回归？

## B.6 报告

**只输出到聊天算失败。** 必须落盘，否则发现会丢失。

报告至少覆盖：

| 章节 | 内容 |
|---|---|
| 结论摘要 | 严重性分布 + 总体判断 + 关键指标 |
| 变更概览 | 改了什么、多大、涉及哪些面 |
| 发现 | 每条含位置、来源提交、爆炸半径、测试覆盖、历史上下文、攻击场景 |
| 测试覆盖分析 | 缺口在哪、为什么算缺口 |
| 爆炸半径分析 | 数字与分级 |
| 历史上下文 | 删掉的代码来自哪里、是不是安全修复、有没有回归 |
| 建议 | 分三级：立即阻断 / 上生产前 / 技术债 |
| 分析方法 | 用了什么策略、**局限是什么**、置信度 |
| 附录 | 证据 |

> **「局限」一节不是走过场。** 没测什么、为什么没测，必须写清楚——
> 读者据此判断这份报告的结论能覆盖到哪。

**不适用的场景**（明说，不要硬套）：全新代码（无基线可比）、纯文档改动、格式化/lint、
提问者明确只要快速摘要并接受风险。

## B.7 与阶段 C 的衔接

**本阶段报出的每一条疑似发现，都必须逐个走阶段 C 验证，不许直接当结论写进报告。**

阶段 B 产出的是「疑点」，阶段 C 才产出「裁定」。
把疑点当结论，就是本项目要解决的那个问题本身。
