# 阶段 A：依赖面审计

> 审的是「你依赖的东西」，不是「你自己的代码」。回答：**这次引入/升级的依赖，带来了什么风险？**
>
> 前置：`../SKILL.md` 的三条不可跳过规则。**本阶段从不读依赖的源码。**

---

## A.0 这个阶段做什么、不做什么

| 做 | 不做 |
|---|---|
| 确认清单文件与锁文件、解析精确版本 | 判断项目能不能安装、能不能构建（**从不安装、从不构建、从不执行**） |
| 用确定性工具取漏洞、陈旧度、维护状态 | 许可合规审计 |
| 把工具结果翻译成判断 | 扫目标自身源码的漏洞或密钥（那是阶段 B / 阶段 C） |
| 说清哪些判据**不可评估** | 对采集器不支持的生态即兴发挥（说「不支持」，不要硬凑） |

**本阶段只读 registry、公告与仓库元数据。**

---

## A.1 为什么不自己造测量工具

本框架**刻意不重写**依赖扫描。原因不是懒：

1. 已有成熟工具覆盖了这件事，重写只会引入新风险，而测量逻辑本身必须是确定性的
2. 漏洞数据源（OSV 等）是持续更新的，自建副本必然过期
3. **这个阶段的价值在判断，不在测量**

所以本阶段的产出器是**编排层**：调用现成工具、把它们的输出归一成事实、标注哪些没测。

可用的发现源（装哪个用哪个，**装前先审计源码**）：

| 用途 | 候选 |
|---|---|
| 依赖漏洞（含修复版本） | 任何基于 OSV 的扫描器 |
| 锁文件与清单解析 | 工具自带，或 `npm ls` / `pnpm why` 这类包管理器命令 |
| 引入时间（哪个提交加进来的） | `git log --oneline --follow -- <锁文件>` |

> ⚠️ **装载检测与降级**：这些工具**一个都没装**也要能跑完流程。
> 降级时如实标注「本判据未评估」，**不要**用模型记忆里的 CVE 数据顶上——
> 那正是本框架禁止的事。

## A.2 第一步：确认输入

**目标目录必须有** `package.json` / `pyproject.toml` / `requirements*.txt` / `go.mod` 之一。
没有就**直接说没有并停止**，不要为一个采集器不解析的生态即兴审计。

**能精确解析版本的**：`package-lock.json`、`npm-shrinkwrap.json`、`uv.lock`、Go 1.17+ 的 `go.mod`。

**不能的**：`yarn.lock`、`pnpm-lock.yaml`、`poetry.lock`。
存在这些时要**明说**，版本回退到 pin 或最新发布版，并标注这是近似。

**检查网络身份**：未认证的 GitHub API 只有 60 次/小时。采集器每个依赖要发若干请求，
未认证时仓库类判据会大面积不可评估——**说出来，而不是悄悄降级或重试到死**。

---

## A.3 三态，不是两态

每个依赖、每条判据，只能落到三种状态之一：

| 状态 | 含义 |
|---|---|
| 已评估 · 干净 | 确实查过，且在这个判据下没问题 |
| 已评估 · 标记 | 确实查过，有问题 |
| **因某原因不可评估** | 没查成——**这一项必须写明原因** |

**缺失的测量绝不是干净的结论。**

采集器非零退出时，它是在**拒绝报告**——**逐字转述它的消息，不要重试、不要绕过**。
一个什么都没测到的运行，产出的是「不可评估」，**不是**「没发现问题」。

### 引用纪律

- 「无公告」只意味着「在**被评估的范围内**没有」——引用干净结论之前先看覆盖表
- **数字必须逐字引用**，不得重新推导、四舍五入或修饰
- **没发现不等于背书**

---

## A.4 模型能加、采集器加不了的部分

测量归工具，判断归模型。以下是模型该加的价值：

| 加什么 | 注意 |
|---|---|
| 这个读者**该先动哪个** | 按风险排序，不要按字母序 |
| 升级路径 | 补丁版还是大版本？大版本意味着破坏性变更 |
| 废弃依赖的替代候选 | **命名前先验证候选在 registry 里确实存在**，并标注这是判断而非测量 |
| 安装脚本风险 | 被标记的安装脚本能否用 `--ignore-scripts` 规避 |

---

## A.5 报告文体

本阶段的报告常被**逐字粘进工单**，所以：

- 无人称、无缩略、无感叹号
- 主动语态且**以事为主体**：写「升级到 1.19.0 清掉全部 25 条公告」，不写「建议升级 axios」
- 不用强化词（very / significant / fortunately）
- **不做动机猜测**
- 时态：审计动作用过去时，依赖状态用现在时，后果用将来时
- 建议只说**动作与代价**，**不指认责任方**

---

## A.6 与阶段 C 的衔接

依赖审计报出的问题通常**不需要**走阶段 C——它们的证据来自漏洞数据库，本身就是确定的。

但有一类例外：**「这个漏洞在本项目里是否真的可达」**。
如果某个依赖漏洞的受影响函数在你这里根本没有调用路径，那它是一个**需要判定的断言**，
不是既成事实。遇到这种，走阶段 C。
