# 元机制：让流程真正生效的六件事

> 阶段 A / B / C 是**流程**。这份文件是让流程不至于退化成走过场的**机制**。
>
> 它们的共同点是：**都不靠自觉**。凡是靠「记住要仔细」的约束，在长会话里都会失效。

---

## 一、防「算错数」：测量与判断分离

**规则**：凡是可测量的量，一律由命令或脚本产出。模型只做判读。

调用方数量、测试覆盖率、依赖版本、行号、提交哈希、函数被调用几次——
**这些一律不许靠印象回答**。工具不可用时说「不可测量」，**不许估算后当成事实写进结论**。

### 为什么这条必须硬化

模型估算这类数字不是「不太准」，而是**系统性错误**，并且错得让人察觉不到：

- 某个包在代码托管平台上显示 5+ 人维护，而它在包管理器里的实际权限列表只有 **1 人**
- 一个每周下载 1.6 亿次的包，在某个数据源里显示**零下载**

这两个都是实测翻车案例。它们说明的不是「要更小心」，而是
**手感估数字这件事本身不可靠，无论怎么努力**。

### 落地

本项目为此提供了产出器，并定义了契约（`fact-contract.md`）：

```powershell
# <euthyna 仓库> = 本项目检出的位置，不是被审计项目的路径
node <euthyna 仓库>/bin/euthyna.js history  --base <rev> --repo <被审计的仓库>
node <euthyna 仓库>/bin/euthyna.js coverage --coverage <file> --symbol <name>
```

⚠️ 写成相对的 `node bin/euthyna.js` 会失败：审计时当前目录是被审计的项目。
命令、退出码与失效情形见 `fact-producers.md`。

## 二、防「报假货」：证据强制 + 门槛二分

### 2.1 证据强制到 `file:line`

- 每条主张引用具体位置：`path:L123`，有版本时写 `path:L123 (commit abc1234)`
- 禁用 `probably` / `likely` / `大概是`——去追真实代码，追不了就**明说追不了**
- 演示代码里禁止 `TODO`、`...`、`// 攻击者在这里做某事`
- **一旦发现演示用了人为绕过**（mock、stub、禁用检查），该演示判定**无效**

### 2.2 「抬高门槛」不等于「消除缺陷」

这是最容易混淆、也最容易导致高估严重性的一处。防护要分两类：

| 类别 | 例子 | 意义 |
|---|---|---|
| **彻底阻止** | Rust 安全类型系统对内存破坏；参数化查询对 SQL 注入 | 该类缺陷不可能发生 |
| **只抬高门槛** | ASLR、栈金丝雀、CFI | 更难，但**没有消除** |

同理要分清：

- **主要安全控制** vs **纵深防御**——主要防护完好时，纵深防御失效**不算缺陷**
- **数学上不可能** / **实践中不可行** / **可行**——三态必须说清，不能混为一谈

## 三、防「漏真货」：双向怀疑 + 三态诚实

只防误报的系统会退化成「什么都说不是」——那和「什么都说有」一样没用。

### 3.1 恶魔代言人必须双向

反对缺陷的问题（防误报）之外，**必须**问这两条：

> **12. 我是否因为利用方式复杂或不太可能，就否定了一个真实的缺陷？**
> **13. 我是否编造了未在源码中验证的缓解措施或校验逻辑？**（得出结论后**重读代码**）

第 12、13 问**任何情况下都要问**。模型的默认偏差是「报太多」，所以大多数机制都在压制它；
**压制过头就会漏掉真漏洞**，这两问是对称的配重。

### 3.2 三态，不是两态

每个判据只能落到：**已评估-干净 / 已评估-标记 / 因某原因不可评估**。

- 一次什么都没测到的运行，产出的是「不可评估」，**不是**「没发现问题」
- 引用任何「干净」结论之前，先看覆盖表
- **数字必须逐字引用**，不得重新推导、四舍五入或修饰
- **没发现不等于背书**

### 3.3 裁定要有第三态

只有「真 / 假」两态时，「没查完」会被迫写成「假」——那是在制造假阴性。

所以裁定必须有 `INCONCLUSIVE`，且**必须写明缺什么、为什么缺**。

## 四、防「偷懒」：预先列举借口

**「要仔细」没有用。有用的是预先列出模型在实际审计中会产生的偷懒念头，逐条封死。**

| 借口 | 为什么错 | 必须做什么 |
|---|---|---|
| 改动很小，快速看一下 | 最严重的历史漏洞可能只有两行 | 按**风险**分类，不按规模 |
| 这个代码库我熟 | 熟悉产生盲区 | 显式建立基线 |
| 翻 git 历史太费时间 | 历史揭示回归 | **不许跳过**来源归属 |
| 影响面一眼就能看出来 | 会漏掉传递调用者 | 定量计算 |
| 没有测试不是我的问题 | 缺测试 = 风险升级 | 写进报告并**提升**严重性 |
| 只是重构，没有安全影响 | 重构会破坏不变量 | 在**证明**为低风险之前一律按高风险分析 |
| 我口头说明就行 | 没有产物 = 发现丢失 | 必须写报告文件 |
| 这个模式看着危险 | 模式识别不是分析 | 完成数据流追踪才能下结论 |
| 相似的代码在别处是漏洞 | 每处的上下文、调用方、防护都不同 | 独立验证本实例 |
| 这明显是严重漏洞 | 模型偏向于看到 bug 并高估严重性 | 完成恶魔代言人复核，用证据证明 |
| 跳过完整验证以省时间 | 不允许部分分析 | 按选定路径执行**全部**步骤 |

**这张表要在每次审计开始时显式加载**，而且**要跟着真实事故增长**——
每发现一次新的偷懒模式就补一行。它是一份活的清单。

## 五、防「丢失」：输出必须落盘

- **只输出到聊天算失败**。必须写报告文件
- 写文件失败时的降级顺序：当前工作目录 → 桌面 → 临时目录 → **最后手段**才输出到聊天并提示手动保存
- 文件名带项目名与日期

设计意图：聊天记录会滚走、会被压缩，**文件不会**。一份交付物的存续不该依赖会话的长度。

## 六、防「污染」：能力按阶段隔离

### 6.1 门禁不可委派

有些阶段需要**跨阶段的综合判断**，把它们交给子代理等于把责任切碎：

- 影响评估
- 恶魔代言人复核
- 门禁裁定

**这三项不得委派。**

### 6.2 子代理权限刻意不对称

| 角色 | 权限 |
|---|---|
| 数据流分析 | **只读** |
| 可利用性验证 | **只读** |
| 演示构建 | 唯一可写 |

理由：**制造证据的能力只集中在一个阶段**。前置阶段只能观察——
如果分析阶段就能写文件，它就能「顺便」把证据改成支持自己结论的样子。

### 6.3 依赖未完成，绝不开始下一阶段

任务开始时标 in-progress，**只有具体证据才能标 completed**。
并行子阶段并发启动，进入下一依赖门禁前**收齐所有结果**。

---

## 这六条之间的关系

```
一、测量与判断分离 ─┐
                   ├─→ 让「事实」可信
二、证据强制 ──────┘
                   ├─→ 让「结论」可信
三、双向怀疑 ──────┘
四、借口表 ───────────→ 让流程不被绕过
五、落盘 ─────────────→ 让产出存续
六、能力隔离 ─────────→ 让流程不被污染
```

前三条决定**结论质量**，后三条决定**流程质量**。缺任何一条，整套东西都会在某个环节退化。
