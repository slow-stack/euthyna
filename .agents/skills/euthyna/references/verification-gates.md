# 阶段 C：结论面验证（判定层）

> **定位**：不找 bug，只判定已有疑似 bug 的真假。
> 触发语是「这是真的吗」「验证这个发现」「是否可利用」。
>
> 本文件是 euthyna 的核心资产。测量层谁都能做，**判定纪律才是差异点**。
> 方法论来源与许可见 `NOTICE.md`。

---

## C.0 第零步：重述断言（不可跳过）

用自己的话重述，逐项写下来。**不许直接进入分析。**

| 要重述的 | 说明 |
|---|---|
| 确切漏洞主张 | 一句话，可判真假 |
| 声称的根因 | 缺陷在**哪里**、**为什么** |
| 声称的触发方式 | 攻击者做什么 |
| 声称的影响 | 落到 RCE / 提权 / 信息泄露 |
| **威胁模型** | 代码以什么权限运行？是否沙箱？攻击者触发前已经能做什么？ |
| 缺陷类别 | 9 类之一（见 `bug-classes.md`） |
| 执行上下文 | 单线程？有同步？生命周期？ |
| 调用者分析 | 谁调用它、以什么参数 |
| 架构上下文 | 它在系统里处于什么位置 |
| 历史上下文 | 这段代码是何时、为何加进来的 |

> **一半的误报在这一步就崩塌了**——当断言被精确重述时，它根本讲不通。
> 所以这一条不是形式主义：它是性价比最高的过滤器。

**产出**：把重述结果写成事实契约里的 `subject.claim`（见 `docs/fact-contract-zh.md`）。

## C.1 路由：标准验证 vs 深验证

### 走标准验证（线性单遍清单）——需**全部**满足

- 断言清晰具体
- 单组件（无跨组件交互）
- 缺陷类别已知
- 无并发或异步
- 数据流直白

### 走深验证（任务化编排 + 子代理）——**任一**满足即走

- 断言含糊、可有多种解读
- 跨组件（数据流经 3 个以上模块）
- 涉及竞争条件或 TOCTOU
- 逻辑缺陷且无明确 spec 可比对
- 标准验证走不出结论，或被升级
- 用户明确要求

**默认从标准开始。** 标准验证内置两个升级检查点：

1. Step 1 之后：若出现 3 个以上信任边界、回调/异步控制流，或含糊的校验链 → 升级
2. Step 5 之后：若任一问题产生无法解决的真实不确定性 → 升级

**升级时交出迄今全部证据**，深验证从停下的地方继续，**不重复已完成的工作**。

## C.2 标准验证 6 步

### 第 1 步：数据流

1. 绘制跨越的信任边界（内部可信 vs 外部不可信）
2. 识别 source 与 sink 之间**所有**校验与净化
3. 查 API 契约——有些 API 自带边界保护
4. 查环境防护，并**区分**「彻底阻止」与「只抬高门槛」
5. 应用对应缺陷类别的专项检查（`bug-classes.md`）

> **陷阱：孤立分析代码。** 上游的条件逻辑可能让缺陷在数学上不可达。
> 必须追完整校验链，不能只看危险操作附近那几行。

### 第 2 步：可利用性

- **攻击者控制**：可信组件写入的内部存储**不是**攻击者可控的
- **边界证明**：写出显式代数证明，验证「IF 校验通过 THEN 边界保证成立」
- **竞争可行性**：单线程初始化、已同步的上下文**不可能**有竞争

### 第 3 步：影响

- 区分**真实安全影响**（RCE、提权、信息泄露）与**运维健壮性**（崩溃恢复、清理失败）
- 区分**主要安全控制**与**纵深防御**

### 第 4 步：演示草图

```
数据流: [Source] → [校验?] → [变换?] → [脆弱操作] → [影响]
```

写清：攻击者控制什么、怎么控制、触发伪代码。

### 第 5 步：恶魔代言人抽查（7 问）

反对 5 问（防**假阳性**）+ 支持 2 问（防**假阴性**，标为 always ask）。

见 C.5。

### 第 6 步：门禁复核

走全部 6 门禁 + 全部 13 条误报清单。

## C.3 六个门禁（全部通过才可报为漏洞）

| # | 门禁 | 判据 | 通过 | 失败 |
|---|---|---|---|---|
| 1 | **流程** | 所有阶段完成且有书面证据 | 每阶段都有证据 | 阶段缺具体证据 |
| 2 | **可达性** | 攻击者能到达并控制该处数据 | 有攻击者控制路径的明确证据 + PoC 确认 | 无法证明控制或可达 |
| 3 | **真实影响** | 利用导致 RCE、提权或信息泄露 | 有具体场景的直接影响 | 仅运维健壮性问题 |
| 4 | **PoC 验证** | PoC 演示了攻击路径 | 展示了控制、触发与影响 | PoC 未能展示路径或影响 |
| 5 | **数学边界** | 数学分析确认脆弱条件可能发生 | 代数证明条件可能 | 数学证明校验阻止了它 |
| 6 | **环境** | 没有环境防护能完全阻止利用 | 防护未消除漏洞 | 环境防护完全阻断 |

### 裁定规则（写死）

| 条件 | 裁定 |
|---|---|
| 6 门禁**全部** `pass` | `TRUE POSITIVE` |
| 任一门禁 `fail` | `FALSE POSITIVE` |
| 无 `fail`，但有 `not_evaluated` | **`INCONCLUSIVE`** |

**关键规则**：任一阶段验证失败，要**记录失败证据并继续执行剩余阶段**；
只有**全部阶段完成后**才下 `FALSE POSITIVE` 裁定。

> `INCONCLUSIVE` 是 euthyna 相对 Trail of Bits 原始定义**新增**的出口。
> 原因：原始实现靠 Stop hook 无限强制继续直到补完，而 DSH 的 Stop hook
> **必须自带限流**（否则死循环），做不到无限强制。详见 `docs/dsh-stop-gate-zh.md`。

### 裁定格式（必须带证据）

```
BUG #3 FALSE POSITIVE — packet_handler.c:142 的整数下溢
  门禁 5（数学边界）FAIL：第 98 行校验保证 packet_size >= 16，
  故 (packet_size - header_size) >= 8。下溢在数学上不可能。

BUG #4 TRUE POSITIVE — 命令注入
  门禁全部通过。证据：src/archive.js:42 (abc1234)
  复现：node tools/poc.js
  可利用性：EASY
  影响：以服务账号执行任意命令
```

**格式由机器强制**：写完后用 `euthyna gate <报告文件>` 校验（见 SKILL.md「门禁的
程序化校验」一节）。TRUE POSITIVE 缺证据、缺复现、或带了 FAIL 门禁，会被校验器
**降级为「观察」**并以退出码 10 报出——纪律不依赖裁定者的自觉。

## C.4 十三条误报清单（对**每个**疑似缺陷逐条应用）

| # | 条目 | 要问的问题 |
|---|---|---|
| 1 | **追踪完整校验链** | 危险操作之前，所有先行的校验是什么？不要分析孤立片段 |
| 1a | **映射完整条件逻辑流** | 看起来不安全的 `buffer[length-4]` 是否只在 `length > 12` 时可达？ |
| 2 | **识别防御性编程** | `ASSERT(size == expected)` 是防御，不是漏洞 |
| 3 | **确认可利用的数据路径** | 只报有**已确认**可利用数据流的漏洞；不要假设网络数据会到达危险函数 |
| 4 | **理解数据源上下文** | API 返回值、编译期常量、网络数据的风险等级不同。判定真实来源 |
| 5 | **分析边界校验逻辑** | 若校验了 `size >= MIN` 且 `MIN >= sizeof(header)`，减法**不可能**下溢 |
| 6 | **核验 TOCTOU 主张** | 被检查的值能在检查与使用之间改变吗？同函数内检查后立即使用且无外部修改 = 无 TOCTOU |
| 7 | **理解 API 契约与信任边界** | 有些 API 自带边界保护，无论输入如何都不越界写 |
| 8 | **区分内部存储与外部输入** | 配置存储、注册表由可信组件控制，**不是**攻击者可控 |
| 9 | **不要把模式识别当成漏洞分析** | 「看着脆弱」的代码可能因上下文与 API 契约而安全 |
| 10 | **核验并发访问确实可能** | 单线程初始化上下文不可能有竞争；核验线程模型与同步机制 |
| 11 | **评估真实 vs 理论影响** | 非关键数据的存储失败是运维问题。问：会导致代码执行、提权或信息泄露吗？ |
| 12 | **区分纵深防御与主要控制** | 主要防护存在时，纵深防御失效不一定是漏洞 |
| 13 | **严格而非表面地应用本清单** | 有清单不等于防住误报。**每个**疑似漏洞都要走完**全部**条目 |

## C.5 恶魔代言人（双向对称怀疑）

这是全套设计里最精妙的一处：**它同时防假阳性和假阴性**。

### 反对缺陷（11 问，防假阳性）

1. 我是否在**幻觉**这个缺陷？（模型偏向于到处看到 bug 并把它们全评为 critical）
2. 我是否在做**模式匹配**而非分析？
3. 我是否**混淆了信任边界**？
4. 我的证明是否**严谨**？（有没有「大概率」「应该」）
5. 我是否把**纵深防御**当成了主要控制？
6. 攻击者真的**控制**这个输入吗？
7. 这个路径真的**可达**吗？
8. 我是否**忽略了上游的校验**？
9. 环境防护是否**完全阻止**了利用？
10. 影响是**真实的**还是运维层面的？
11. 我是否**高估了严重性**？

### 支持缺陷（2 问，**任何情况下都要问**，防假阴性）

12. **我是否因为利用方式复杂或不太可能，就否定了一个真实的缺陷？**
13. **我是否编造了未在源码中验证的缓解措施或校验逻辑？**
    → 得出结论后**重读代码**。

> 第 12、13 问是防假阴性的关键。模型的默认偏差是「报太多」，
> 所以大多数防误报机制都在压制它；但压制过头就会漏掉真实缺陷。
> 这两问是对称的配重，不许跳过。

## C.6 深验证的任务依赖结构

```
Phase 1: 1.1 绘信任边界 + 追数据流
           ├─ 1.2 研究 API 契约与安全保证   ┐
           ├─ 1.3 环境防护分析             ├─ 均被 1.1 阻塞
           └─ 1.4 交叉引用分析             ┘
Phase 2（被 P1 阻塞）: 2.1 确认攻击者控制输入 ┐
                       2.2 数学边界验证       ├─ 并行
                       2.3 竞争条件可行性证明 ┘
                       └→ 2.4 对抗性分析（被 2.1/2.2/2.3 阻塞）
Phase 3（被 P2 阻塞）: 3.1 证明真实安全影响 ┐ 并行
                       3.2 主要控制 vs 纵深防御 ┘
Phase 4（被 P3 阻塞）: 4.1 伪代码 PoC + 数据流图（始终必做）
                       ├─ 4.2 可执行 PoC（若可行）  ┐
                       ├─ 4.3 单元测试 PoC（若可行）├─ 并行
                       └─ 4.4 Negative PoC          ┘
                       └→ 4.5 验证 PoC 确实演示漏洞
Phase 5（被 P4 阻塞）: 5.1 恶魔代言人复核（13 问）
Gate Review（被 P5 阻塞）: 6 门禁评估 → 裁定
```

### 执行规则

- 任务开始时标 in-progress，**只有具体证据才标 completed**
- 并行子阶段用子代理并发启动；进入下一依赖门禁前**收齐所有结果**
- **依赖未全部完成，绝不开始该阶段**
- **Phase 3 / Phase 5 / Gate Review 不得委派**——它们需要跨阶段综合

### 子代理权限刻意不对称

| 子代理 | 权限 |
|---|---|
| 数据流分析 | **只读** |
| 可利用性验证 | **只读** |
| PoC 构建 | 唯一有写权限 |

**制造证据的能力只集中在一个阶段**，前置阶段只能观察——降低污染证据的风险。

## C.7 PoC 规则

### 可行性跳过条件（跳过必须带理由）

**可执行 PoC**：

- 需要本地不可用的硬件或网络
- 目标语言运行时未安装
- 利用需要**修改**生产代码（而非调用它）
- 缺陷在闭源组件

**单元测试 PoC**：

- 项目没有测试基础设施
- 脆弱代码无法孤立调用（深依赖链且无测试夹具）
- 构建系统损坏

### PoC 验证 5 问

1. 伪代码是否准确追踪了第 1 步的数据流？
2. 可执行 PoC 是否**真的运行**并展示影响？（要捕获**真实输出**，不是预期输出）
3. 单元测试是否通过并演示问题？
4. Negative PoC 是否正确识别了前置条件？
5. **是否存在人为绕过**（mock、stub、禁用检查）？——**有则 PoC 无效**

### Negative PoC 的作用（不许省）

展示同一路径在**良性输入**下正常工作 → 展示利用所需的**具体前置条件** →
解释为何正常使用下不成立但攻击者可强制成立。

**这不是证明缺陷是假的**，而是记录安全与不安全条件的差量，对修复有用。

## C.8 批量分诊

多个疑似 bug 时：

1. 先对**全部**跑第零步（重述常直接瓦解明显的误报）
2. 逐个独立路由
3. **先处理全部标准路由的，再处理深路由的**
4. 全部验证完后，检查**利用链**——单独未过门禁的发现可能组合成可行攻击

## C.9 最终汇总格式

1. 计数：X 个 TRUE POSITIVE、Y 个 FALSE POSITIVE、Z 个 INCONCLUSIVE
2. TRUE POSITIVE 列表：每条附简要漏洞描述
3. FALSE POSITIVE 列表：每条附简要拒绝理由
4. INCONCLUSIVE 列表：**每条附缺什么、为什么缺**
