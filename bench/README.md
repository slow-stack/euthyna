# 召回率靶场

## 这个靶场测什么

**测「判定」的召回率，不测「发现」的召回率。**

euthyna 不是扫描器，它不找 bug。拿它去测「能不能发现漏洞」是问错了问题。
正确的问题是：**给定一条关于某个漏洞的断言，这套纪律能否得出正确的裁定？**

于是需要一张混淆矩阵：

| | 裁定为 TRUE POSITIVE | 裁定为 FALSE POSITIVE |
|---|---|---|
| **实际是真漏洞** | ✅ 正确 | ❌ **漏报——最危险的一格** |
| **实际不是漏洞** | ❌ 误报 | ✅ 正确 |

## ground truth 怎么来的

**不靠声称，靠执行。**

- 每个「真」案例都配一个**真的能利用成功的 PoC**（`exploits.js`）。
  跑不通的不算真漏洞，不许进「真」集合。
- 每个「假」案例都要么**结构上不可达**，要么**守卫完整**，
  并在 `meta.json` 里写明"为什么不是漏洞"以及这个判断是怎么验证的。

## 关键设计：假案例都是真案例的近邻

这是靶场有没有价值的分水岭。

如果假案例只是「明显无害的代码」，那它测的是常识，谁都过得去。
所以每个假案例都和某个真案例**共用同一个模式**，只差一道守卫：

| 真案例 | 对应假案例 | 差别只在 |
|---|---|---|
| 原型链污染（无守卫的深合并） | 同一个合并函数 + `__proto__` 拦截 | 一道 key 过滤 |
| 路径穿越（直接拼路径） | 同一个读取函数 + 规范化与白名单 | 三行校验 |
| 命令注入（`exec` 拼字符串） | 同一次备份调用改用 `execFile` 传数组 | 换个 API 而已 |
| 代码注入（对输入 `new Function`） | 同一个 `new Function`，但前面有 early return | 可达性 |
| 归档输出路径穿越（tar `-czf` 目标拼接） | 同一输出路径 + 归属检查 | 一道归属检查 |
| 归档成员读取（tar 成员名拼接） | 同一成员名 + 分隔符拒绝 | 一道成员名校验 |
| 开放重定向（`Location` 直填调用方 URL） | 同一跳转 + 目的地 host 白名单 | 一份白名单 |
| SSRF（对请求体 URL 直接 `http.get`） | 同一取回 + 目的地 host 白名单 | 一份白名单 |
| — | 危险代码**在注释里** | 一个字都不差，只是没执行 |
| — | 危险代码**在测试夹具里** | 不在出厂产物内 |

后四对来自 `DESIGN-round3.md` 的预注册设计；同一份归档源码在 p3b/p5/p6 三个案例下
带着三条不同断言、得到三个不同裁定——裁定对象是断言，不是代码库。

后两个来自 axe-core 那次实跑的教训：**误报的最大单一来源是范围，不是模式**。

## 目录结构

```
bench/
├── README.md
├── cases/<id>/
│   ├── claim.md       ← 裁定者只看到这个 + src/
│   ├── src/           ← 被审代码
│   └── meta.json      ← ground truth，裁定者看不到
├── exploits.js        ← 证明「真」案例真的可利用
└── score.js           ← 拿裁定结果算混淆矩阵
```

## 怎么跑

```powershell
node bench/exploits.js              # 跑通全部 PoC —— 不通过就说明「真」集合不可信
node bench/prepare-blind.js         # 生成不透明编号的盲副本到 .scratch/blind/
node bench/score.js verdicts.json   # 用裁定结果算混淆矩阵
```

**平台契约**：exploit 的 ground truth 定义在 **bsdtar** 的操作数语义上
（`@` 归档并入、裸 `..` 成员——见 p6/p6b 的 `meta.json` 与 `RESULTS-round3.md`）。
在 `tar` 是 GNU tar 的平台上这两条语义不存在，`node --test` 里的 ground truth
守卫会**带原因跳过**而不是失败——truth 在那个二进制上不是被破坏了，而是未定义。
Windows 的 `tar` 是 bsdtar，CI 的三个 Windows job 照常全量运行该守卫。

**裁定必须是盲的**：裁定者只看自己的 `case-NN/`，不看 `meta.json`、不看别的案例、
不看 `RESULTS.md`。自己做完再看答案，等于没测。

### ⚠️ 盲测最大的敌人是裁定者自己的上下文

第二轮实测发现了一条会**自我再生**的污染通道：

```
裁定结果写进主对话 → 记忆插件自动摘要 → 存进跨会话记忆库
      → 下一次裁定启动时被注入 → 下一个裁定者读到答案
```

也就是说：**每收到一份结果，就等于给后面的裁定者递了一次答案。**
第一次清理后约两分钟就长出了新的一批，其中直接写着某两个案例的裁定词。

而且注入**不是只给相关的**：一个案例的裁定者读到了**另一个案例**的文件位置
与调用链。那次是裁定者自己主动报告并提示复核的。

**协议要求（缺任何一条，这轮结果就作废）：**

1. **结论只写文件，不回传对话。** 裁定者把完整报告写到
   `%TEMP%\euthyna-blind-results\case-NN-runN.md`，只回一行 `DONE <id>`。
   回传的那一行也不得包含结论，最多一个词。
2. **开跑前清空记忆库里一切与案例有关的条目，并用探针验证清干净了。**
   只归档搜索命中的远远不够——实测漏掉了三分之一，是分页枚举全库才找齐的。
3. **每个裁定者必须申报三件事**：① 有没有被注入记忆、注入了什么；
   ② 有没有越界读允许范围之外的文件；③ 分析代码之前有没有已经知道答案。
   任一条答「是」，该次运行作废重跑。
4. **`AGENTS.md` 是最后一条关不掉的通道**：它自动进入每个裁定者的上下文，
   而仓库地图点名了 `bench/RESULTS.md` 是结果文件。只能靠提示词禁止越界读
   加申报来挡。要彻底关掉，只能让裁定者不在本仓库内运行。
5. **不许列举结果目录。** 实测有裁定者在自查时列了 `%TEMP%\euthyna-blind-results\`，
   从文件名与大小看出了兄弟案例的存在。要自查落盘，只许按精确路径读回自己的文件。

### 用探针验证上下文，不要假设

诊断注入是否还在，最直接的办法是**让子代理报告自己的上下文**——它不需要读任何文件：

> 「你的上下文里有没有注入的跨会话记忆？逐条列出 type 与标题。
> 有没有 `case-NN` 形式的编号？有没有针对具体编号的裁定词？
> 只报告，不读文件、不运行命令、不搜索。」

这个探针同时能发现新问题（第二轮就是靠它拍到「bench 10/10」仍然挂在注入内容里）。
注意：**注入切片每轮都会换**，所以一次测得「干净」只对那次快照成立，
不能当成永久状态。

## 局限（先说清楚）

- 案例是**刻意构造**的，不是真实项目的漏洞。它能测「纪律能不能区分真伪」，
  不能测「在真实代码里能不能找到」。
- 样本量小（18 个案例），结论只能当**方向性信号**，不能当统计结论。
- 裁定者是 LLM，同一个案例多跑几次结果可能不同。第一轮每案只跑一次；
  第二轮改为**每案重复 3 次**并报告翻转情况（见 `RESULTS-round2.md`）。
- **真实漏洞那一行只有 4 个样本**，召回率的置信区间很宽。
- **不测「发现」能力**：所有裁定都是拿现成断言做的。
