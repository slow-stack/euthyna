## 0. 三个原插件覆盖了审计的三个环节

它们不是三个竞争方案，而是同一条流水线的三段，各自解决一个**不同环节**的失败模式：

| 环节 | 原插件 | 审什么 | 主要失败模式 | 强制手段 |
|---|---|---|---|---|
| 入口层 | `supply-chain-risk-auditor` | 依赖面（npm/PyPI/Go + lockfile 全树） | LLM 用手感估数字，全估错 | 确定性脚本测量，测量为空则非零退出 |
| 主体层 | `differential-review` | 变更面（PR / commit / diff） | 凭规模判断风险、跳过 git 历史 | 7 阶段 + 决策树 + 质量检查清单 |
| 出口层 | `fp-check` | 结论面（已发现的疑似 bug） | LLM 天生爱报 bug 且高估严重性 | 6 门禁 + 13 问恶魔代言人 + hook 停止门禁 |

选这三个而非 `static-analysis`（那是工具编排），是因为它们承载的是**判断纪律**，而不是工具调用——纪律才是跨宿主可迁移的部分。

## 1. 九个跨文件反复出现的元机制

这是三个插件真正的内核。**照搬工具容易，照搬纪律才是关键。**

### M1. 反偷懒借口表（Rationalizations to Reject）

三个插件**都有**这张表，格式统一为三列：`借口 | 为什么错 | 必须做什么`。

它不是泛泛的"要仔细"，而是**预先列举 LLM 在审计中实际会产生的偷懒念头**，逐条封死：

| 借口 | 为什么错 | 必须做什么 |
|---|---|---|
| "小 PR，快速审一下" | Heartbleed 只有 2 行 | 按**风险**分类，不按规模 |
| "我熟这个代码库" | 熟悉产生盲区 | 显式建立基线上下文 |
| "git 历史太费时间" | 历史揭示回归 | 绝不跳过阶段 1 |
| "爆炸半径一眼就看出来" | 会漏掉传递调用者 | 定量计算 |
| "没测试不是我的问题" | 缺测试 = 风险升级 | 写进报告并提升严重性 |
| "只是重构，没有安全影响" | 重构会破坏不变量 | 在证明为 LOW 之前一律按 HIGH 分析 |
| "我口头说明就行" | 没有产物 = 发现丢失 | 必须写报告文件 |
| "这模式看着危险，所以是漏洞" | 模式识别不是分析 | 完成数据流追踪才能下结论 |
| "相似代码在别处是漏洞" | 每处上下文的校验/调用者/防护都不同 | 独立验证本实例 |
| "这明显是 critical" | LLM 偏向看到 bug 并高估严重性 | 完成恶魔代言人复核，用证据证明 |
| "跳过完整验证以提升效率" | 不允许部分分析 | 按选定路径执行全部步骤 |

**DSH 落地要求**：这张表必须在每次审计开始时显式加载，且**新增条目要跟着真实事故走**——每发现一次新的偷懒模式就补一行。

### M2. 确定性测量与 LLM 判断分离

`supply-chain-risk-auditor` 的做法最彻底：**"两个确定性脚本负责测量；你的工作是它们拒绝自动化的那部分判断。"**

它给出了三个实测翻车案例，作为"为什么不能让 LLM 估数字"的铁证：

- GitHub 贡献者数量显示 `lodash` 有 5+ 人维护，而 npm 的 ACL 实际只有 **1 人**
- `gh` 看到一个**每周 1.64 亿次下载**的包显示**零下载**
- 结论：**禁止**用 `gh`、网页搜索或记忆去估算维护者数量、下载量、陈旧度、CVE 历史

**推广规则**：凡是可测量的量（调用者数量、测试覆盖率、依赖版本、行号），一律由脚本/命令产出，LLM 只做判读。

### M3. 诚实标注覆盖边界

两条硬规则，专门防假阴性：

- **不可得数据不是风险证据**。每个判据只能落到三态：已评估-干净 / 已评估-标记 / 因某原因不可评估
- **缺失的测量绝不是干净的结论**。一次什么都没测到的运行会**非零退出**，而不是打印一份"没发现问题"的报告

配套的阅读纪律：
- "无公告"只意味着"在被评估的范围内没有"——引用干净结论前先看覆盖表
- **数字必须逐字引用**，不得重新推导、四舍五入或修饰
- **没发现不等于背书**：一个没有发现的依赖只是"按这些判据量过了"

### M4. 双向对称怀疑（防假阳性 + 防假阴性）

这是全套文档里最精妙的设计。恶魔代言人提问分两组：

**反对缺陷（11 问，防假阳性）**，含自我指涉的一问：
> "我是否在幻觉这个缺陷？LLM 偏向于到处看到 bug 并把它们全评为 critical。"

**支持缺陷（2 问，防假阴性，标记为 always ask）**：
> 12. 我是否因为利用方式复杂或不太可能，就否定了一个真实的缺陷？
> 13. 我是否编造了未在源码中验证的缓解措施或校验逻辑？——**得出结论后重读代码。**

标准验证路径把第 12、13 问标为"任何情况下都要问"。

### M5. 证据强制到 file:line，禁止占位符

- 每条主张必须引用具体 `file:line`；行号引用格式统一为 `file.sol:L123` 或 `file.sol:L123 (commit abc123)`
- 数据流分析代理**明令禁用** "probably" / "likely" —— 去追踪真实代码，追踪不了就明说
- PoC **禁止**出现 `TODO`、`...`、`$XXM`、`// attacker would do X here`
- **一旦发现 PoC 使用了人为绕过**（mocking、stubbing、禁用检查），该 PoC 判定**无效**

### M6. "抬高门槛 ≠ 消除缺陷"

三处文件反复要求把防护二分：

- **Prevents exploitation entirely**（彻底阻止利用）：Rust 安全类型系统对内存破坏、参数化查询对 SQL 注入
- **Raises the bar**（只抬高门槛）：ASLR、栈金丝雀、CFI —— 更难，但不消除

同理区分：
- **主要安全控制** vs **纵深防御** —— 主要防护完好时，纵深防御失效**不算缺陷**（例：token 若在服务端本就是一次性设计，清理失败不 critical）
- **数学上不可能** / **实践中不可行** / **可行** —— 三态必须说清，不能混为一谈

### M7. 按缺陷类别切换默认假设

`bug-class-verification.md` 对 9 大类给出各自的专项要求，其中最反直觉的是**默认假设的方向按类别翻转**：

- **内存破坏**：safe Rust、未用 `unsafe.Pointer`/cgo 的 Go、托管语言（Java/C#/Python）中的内存破坏**几乎总是误报** —— 除非编译器 bug 或 soundness hole
- **逻辑缺陷**：反过来 —— "逻辑缺陷会通过每一个边界检查和数学证明"，**不能让干净的静态分析说服你它是误报**，必须对照 spec/RFC/设计文档
- **反序列化**：没有 gadget 链，不安全反序列化**只是设计异味，不是可利用缺陷**
- **DoS 复杂度**：必须证明实际最坏输入能触发，**不要只声称 O(n²)**

### M8. 输出持久化优先于聊天

- 差分审查**必须**产出报告文件，9 个强制章节；只输出到聊天算**失败**
- 写文件失败时的降级顺序：当前工作目录 → 用户桌面 → `~/.claude/skills/.../output/` → 临时目录 → **最后手段**才输出到聊天并提示用户手动保存
- 文件名格式：`<PROJECT>_DIFFERENTIAL_REVIEW_<DATE>.md`

### M9. 门禁不可委派 + 权限按阶段隔离

- 6 个门禁是**唯一出口**；Phase 3（影响）、Phase 5（恶魔代言人）、Gate Review **明确禁止委派**——它们需要跨阶段综合
- 深验证要求"依赖未全部完成，绝不开始下一阶段"
- 三个子代理的权限刻意不对称：
  - `data-flow-analyzer`：**只读**（Read/Grep/Glob）
  - `exploitability-verifier`：**只读**（Read/Grep/Glob）
  - `poc-builder`：唯一有 Write/Edit/Bash

  即：**制造证据的能力只集中在一个阶段**，前置阶段只能观察，降低污染证据的风险。

## 2. 方法论本体

### 阶段 A：依赖面审计（轻量、可独立跑）

**前置**：确认目标目录有 `package.json` / `pyproject.toml` / `requirements*.txt` / `go.mod`。没有就**直接说没有并停止**，不要手工为一个采集器不解析的生态即兴审计。

**流程**：
1. 确认清单文件与 lockfile 类型。支持精确版本解析的：`package-lock.json`、`npm-shrinkwrap.json`、`uv.lock`、go 1.17+ `go.mod`。**不支持** `yarn.lock`、`pnpm-lock.yaml`、`poetry.lock` —— 存在时要**明说**，版本回退到 pin 或最新发布版
2. 检查 `gh auth status`。未认证的 GitHub 只有 60 次/小时（认证后 5,000），采集器每个依赖要发若干请求；未认证时仓库类判据会大面积不可评估 —— **说出来，而不是悄悄修**
3. 采集 → 渲染 → 阅读 → 补判断。输出放在被审仓库**之外**
4. 采集器非零退出时，它是**在拒绝报告**：逐字转述它的消息，**不要重试或绕过**
5. 补充 LLM 能加而采集器加不了的：该读者该先动什么、升级路径（补丁版还是大版本）、废弃依赖的替代候选（**命名前先验证候选在 registry 里存在**，并标注这是判断而非测量）、被标记的安装脚本能否用 `npm ci --ignore-scripts` 规避

**文体规范**（回复会被逐字粘进工单）：无人称、无缩略、无感叹号；主动语态且以事为主体（"升级到 1.19.0 清掉全部 25 条公告"，而非"建议升级 axios"）；无强化词（very / significant / fortunately）；不做动机猜测；审计动作用过去时，依赖状态用现在时，后果用将来时；建议只说动作与代价，**不指认责任方**。

**禁止**：许可合规审计、扫目标自身源码的漏洞或密钥（本阶段只读 registry/公告/仓库元数据，**从不读依赖源码**）、判断项目能否安装或构建（**从不安装、构建或执行任何东西**）、npm/PyPI/Go 之外的生态（说"不支持"而不是即兴发挥）。

### 阶段 B：变更面审计（主体，7 阶段）

**核心原则**：风险优先 / 证据为本 / 自适应 / 诚实 / 产出驱动。

#### Pre-Analysis：基线上下文构建（第一动作）

在 base commit 上建立：系统级不变量、信任边界与权限级、校验模式（纵深防御在哪）、关键函数的完整调用图、状态流、"代码本应做什么"。

**为什么**：变更分析需要判断"是否违反了基线不变量""是否破坏了纵深防御"，没有基线就只能凭感觉。

#### Phase 0：接收与分诊

- 提取变更：`git diff <base>..<head> --stat` / `--name-only`、`git log <base>..<head> --oneline`、`gh pr view <n> --json files,additions,deletions`
- 按**代码库规模**选策略（注意：这是选分析深度，不是选风险）：

  | 规模 | 策略 | 做法 |
  |---|---|---|
  | < 20 文件 | DEEP | 读全部依赖，全量 git blame |
  | 20–200 | FOCUSED | 1 跳依赖，优先文件 |
  | 200+ | SURGICAL | 只做关键路径 |

- 按**风险**给每个文件打分：

  | 级别 | 触发条件 |
  |---|---|
  | HIGH | 认证、加密、外部调用、价值转移、**校验被删除** |
  | MEDIUM | 业务逻辑、状态变更、新增公开 API |
  | LOW | 注释、测试、UI、日志 |

#### Phase 1：变更代码分析

对每个变更文件：读**两个版本** → 逐段 diff 分析（BEFORE / AFTER / CHANGE / SECURITY）→ **对被删除的代码做 git blame** → 查回归（被重加）→ 微观对抗（删掉的代码原本防什么攻击？新代码暴露什么面？改过的逻辑能否绕过？检查是否变弱？）→ 生成**具体**攻击场景（目标 / 前提 / 步骤 / 为什么成立 / 影响）。

**红旗**：
- 从 `fix`、`security`、`CVE` 提交中删除的代码 → **CRITICAL**
- 近期（< 1 个月）加入随后被删除 → **HIGH**
- 回归模式：代码加入 → 因安全原因移除 → **现在又被加回来** = REGRESSION

#### Phase 2：测试覆盖分析

**风险升级规则**：
- 新函数 + 无测试 → MEDIUM 升 **HIGH**
- 修改了校验 + 测试未变 → **HIGH RISK**
- 复杂逻辑（> 20 行）+ 无测试 → **HIGH RISK**

#### Phase 3：爆炸半径

统计每个被修改函数的调用者数量：**1–5 LOW / 6–20 MEDIUM / 21–50 HIGH / 50+ CRITICAL**

优先级矩阵：HIGH 风险 × CRITICAL 半径 = **P0**（深度 + 全部依赖）；HIGH × HIGH/MEDIUM = P1；HIGH × LOW = P2。

#### Phase 4：深度上下文

对每个 HIGH 风险函数：映射完整流程（入口条件 / 状态读 / 状态写 / 外部调用 / 返回值与副作用）→ 追踪内部调用（递归建调用图）→ 追踪外部调用（信任边界、对外的行为假设、重入风险）→ 识别不变量（什么必须**永远**为真、什么**绝不能**发生、变更后是否仍成立）→ **五个为什么** → 横切模式检测（同类校验是否在别处也有？这次是否删掉了其中一个，从而破坏纵深防御）。

#### Phase 5：对抗建模（对所有 HIGH 风险变更）

1. **攻击者模型**：WHO（未认证外部用户 / 已认证普通用户 / 恶意管理员 / 被攻陷的依赖 / 抢跑者）/ WHAT（仅公开 API / 已认证角色 / 特定权限）/ WHERE（具体端点或函数）
2. **攻击向量**：入口点 → 4 步攻击序列（具体调用与参数 → 如何到达脆弱代码 → 代码里发生了什么 → 达成什么影响）→ **可达性证明**（函数确实是 public/external、攻击者确实有权限、路径确实经过真实接口）
3. **可利用性三档**：**EASY**（公开 API、无需特殊权限、单次调用）/ **MEDIUM**（需特定条件或提高的权限、多步骤）/ **HARD**（需特权或罕见条件、需大量资源）
4. **完整利用场景**：起始位置 → 逐步骤（命令与参数 / 为什么有效 / 系统状态变化）→ **具体可测的影响**。影响**禁止**写 "could cause issues"，必须落到确切资金量、具体被提升的权限、具体暴露的数据
5. **与基线交叉比对四问**：是否违反系统级不变量？是否破坏信任边界？是否绕过既有校验模式？是否是为此前已修复问题的回归？

#### Phase 6：报告（9 个强制章节）

执行摘要（严重性分布 + 总体风险 + APPROVE/REJECT/CONDITIONAL + 关键指标：分析文件 X/Y (Z%)、测试覆盖缺口 N、高爆炸半径变更 M、检出的安全回归 P）→ 变更概览 → 严重发现（每个含 file:line、commit、爆炸半径、测试覆盖、历史上下文、攻击场景、PoC、修复建议）→ 测试覆盖分析 → 爆炸半径分析 → 历史上下文（**安全相关删除**与**回归风险**）→ 建议（三级：立即阻断 / 上生产前 / 技术债）→ 分析方法（策略、范围、技术、**局限性**、置信度）→ 附录。

**格式硬要求**：行号引用**始终包含**；状态用 ✅ / ⚠️ / ❌；严重性用 🔴 / 🟠 / 🟡 / 🟢；BEFORE/AFTER 代码块。

**明确不适用的场景**：全新代码（无基线可比）、纯文档变更、格式化/lint、用户明确只要快速摘要（且接受风险）。

**红旗（停下并调查）**：从 `security`/`CVE`/`fix` 提交中删除的代码；访问控制修饰符被移除（`onlyOwner`、`internal` → `external`）；校验被删除且无替代；新增外部调用且无检查；高爆炸半径（50+ 调用者）+ HIGH 风险变更。**这些在快速分诊中也要走对抗分析。**

---

### 阶段 C：结论面验证（误报门禁）

**定位**：**不找 bug**，只判定已有疑似 bug 的真假。触发语是"这是真的吗""验证这个发现""是否可利用"。

#### Step 0：重述断言（不可跳过）

用自己的话重述：确切漏洞主张 / 声称的根因 / 声称的触发方式 / 声称的影响 / **威胁模型**（代码以什么权限运行？是否沙箱？攻击者在触发前已经能做什么？）/ **缺陷类别** / 执行上下文 / 调用者分析 / 架构上下文 / 历史上下文。

> **一半的误报在这一步就崩塌了**——当断言被精确重述时，它根本讲不通。

#### 路由：标准验证 vs 深验证

**标准验证**（线性单遍清单，不做任务跟踪），需**全部**满足：断言清晰具体 / 单组件（无跨组件交互）/ 缺陷类别已知 / 无并发或异步 / 数据流直白。

**深验证**（任务化编排 + 子代理），**任一**满足即走：断言含糊可多解 / 跨组件（数据流过 3+ 模块）/ 涉竞争条件或 TOCTOU / 无明确 spec 可比对的逻辑缺陷 / 标准验证无结论或被升级 / 用户明确要求。

**默认从标准开始**——标准验证内置两个升级检查点：(1) Step 1 后若出现 3+ 信任边界、回调/异步控制流或含糊校验链；(2) Step 5 后若任一问题产生无法解决的真实不确定性。升级时**交出迄今全部证据**，深验证从停下的地方继续，**不重复已完成的工作**。

#### 标准验证 6 步

1. **数据流**：绘制跨越的信任边界（内部可信 vs 外部不可信）→ 识别 source 与 sink 之间**所有**校验与净化 → 查 API 契约 → 查能**彻底阻止**（而非只抬高门槛）的环境防护 → 应用对应缺陷类别的专项检查。**陷阱：孤立分析代码**——上游条件逻辑可能使缺陷数学上不可达，必须追完整校验链。
2. **可利用性**：攻击者控制（可信组件写入的内部存储**不是**攻击者可控）/ 边界证明（写出显式代数证明，验证 `IF 校验通过 THEN 边界保证成立`）/ 竞争可行性（单线程初始化与已同步上下文**不可能**有竞争）。
3. **影响**：区分真实安全影响（RCE、提权、信息泄露）与运维健壮性（崩溃恢复、清理失败）；区分主要控制与纵深防御。
4. **PoC 草图**：`数据流: [Source] → [校验?] → [变换?] → [脆弱操作] → [影响]`；攻击者控制什么、怎么控制；触发伪代码。
5. **恶魔代言人抽查（7 问）**：反对 5 问（模式匹配偏差 / 信任边界混淆 / 证明严谨性 / 纵深防御混淆 / **LLM 幻觉**）+ 支持 2 问（**always ask**，防假阴性）。
6. **门禁复核**：走全部 6 门禁 + 全部 13 条误报清单。

#### 6 个门禁（全部通过才可报为漏洞）

| 门禁 | 判据 | 通过 | 失败 |
|---|---|---|---|
| 1. 流程 | 所有阶段完成且有书面证据 | 每阶段都有证据 | 阶段缺具体证据 |
| 2. 可达性 | 攻击者能到达并控制该处数据 | 有攻击者控制路径的明确证据 + PoC 确认 | 无法证明控制或可达 |
| 3. 真实影响 | 利用导致 RCE、提权或信息泄露 | 有具体场景的直接影响 | 仅运维健壮性问题 |
| 4. PoC 验证 | PoC（伪代码/可执行/单元测试）演示了攻击路径 | 展示了控制、触发与影响 | PoC 未能展示路径或影响 |
| 5. 数学边界 | 数学分析确认脆弱条件可能发生 | 代数证明条件可能 | 数学证明校验阻止了它 |
| 6. 环境 | 没有环境防护能完全阻止利用 | 防护未消除漏洞 | 环境防护完全阻断 |

**裁定格式**：
- `BUG #N TRUE POSITIVE — [简述]`（全部门禁通过）
- `BUG #N FALSE POSITIVE — [拒绝理由]`（任一门禁失败）

**关键规则**：任一阶段验证失败，要**记录失败证据并继续执行剩余阶段**；只有**全部阶段完成后**才下 FALSE POSITIVE 裁定。

裁定须带证据，例如：
```
BUG #3 FALSE POSITIVE — packet_handler.c:142 的整数下溢
  门禁 5（数学边界）FAIL：第 98 行校验保证 packet_size >= 16，
  故 (packet_size - header_size) >= 8。下溢在数学上不可能。
```

#### 13 条误报清单（对**每个**疑似缺陷逐条应用）

1. **追踪完整校验链**——不要分析孤立片段，向前追溯所有先于危险操作的校验
   1a. **映射完整条件逻辑流**——看起来不安全的 `buffer[length-4]` 若只在 `length > 12` 时可达，则漏洞不可能
2. **识别防御性编程模式**——`ASSERT(size == expected_size)` 是防御，不是漏洞
3. **确认可利用的数据路径**——只报有**已确认**可利用数据流的漏洞，不要假设网络数据会到达危险函数
4. **理解数据源上下文**——API 返回值、编译期常量、网络数据风险等级不同；判定真实来源与是否攻击者可控
5. **分析边界校验逻辑**——若校验了 `packet_size >= MIN_SIZE` 且 `MIN_SIZE >= sizeof(header)`，则减法**不可能**下溢
6. **核验 TOCTOU 主张**——需证明被检查的值能在检查与使用之间改变；同函数内检查后立即使用且无外部修改 = 无 TOCTOU
7. **理解 API 契约与信任边界**——有些 API 自带边界保护，无论输入如何都不会越界写
8. **区分内部存储与外部输入**——配置存储、注册表由可信组件控制，**不是**攻击者可控
9. **不要把模式识别当成漏洞分析**——"看着脆弱"的代码可能因上下文与 API 契约而安全
10. **核验并发访问确实可能**——单线程初始化上下文不可能有竞争；核验线程模型与同步机制
11. **评估真实 vs 理论影响**——非关键数据的存储失败是运维问题；问：会导致代码执行、提权或信息泄露吗？
12. **理解纵深防御 vs 主要控制**——主要防护存在时，纵深防御失效不一定是漏洞
13. **严格而非表面地应用本清单**——有清单不等于防住误报，**每个**疑似漏洞都要走完**全部**条目

#### 深验证的任务依赖结构

```
Phase 1: 1.1 绘信任边界+追数据流
           ├─ 1.2 研究 API 契约与安全保证   ┐
           ├─ 1.3 环境防护分析             ├─ 均被 1.1 阻塞
           └─ 1.4 交叉引用分析             ┘
Phase 2（被 P1 阻塞）: 2.1 确认攻击者控制输入 ┐
                       2.2 数学边界验证       ├─ 并行
                       2.3 竞争条件可行性证明 ┘
                       └→ 2.4 对抗性分析（被 2.1/2.2/2.3 阻塞）
Phase 3（被 P2 阻塞）: 3.1 证明真实安全影响 ┐ 并行
                       3.2 主要控制 vs 纵深防御 ┘
Phase 4（被 P3 阻塞）: 4.1 伪代码 PoC + 数据流图（始终必做）
                       ├─ 4.2 可执行 PoC（若可行）  ┐
                       ├─ 4.3 单元测试 PoC（若可行）├─ 并行
                       └─ 4.4 Negative PoC          ┘
                       └→ 4.5 验证 PoC 确实演示漏洞
Phase 5（被 P4 阻塞）: 5.1 恶魔代言人复核（13 问）
Gate Review（被 P5 阻塞）: 6 门禁评估 → 裁定
```

**执行规则**：任务开始时标 in-progress，**只有具体证据才标 completed**；并行子阶段用子代理并发启动，进入下一依赖门禁前**收齐所有结果**；**依赖未全部完成绝不开始该阶段**；Phase 3 / 5 / Gate Review **不得委派**。

**PoC 的可行性跳过条件**（跳过必须带理由）：
- 可执行 PoC：需本地不可用的硬件或网络 / 目标语言运行时未装 / 利用需**修改**生产代码（而非调用它）/ 缺陷在闭源组件
- 单元测试 PoC：项目无测试基础设施 / 脆弱代码无法孤立调用（深依赖链且无 harness）/ 构建系统损坏

**Negative PoC（4.4）的作用**：展示同一路径在**良性输入**下正常工作 → 展示利用所需的**具体前置条件** → 解释为何正常使用下不成立但攻击者可强制成立。**这不是证明缺陷是假的**，而是记录安全与不安全条件的差量，有助于修复。

**PoC 验证 5 问（4.5）**：伪代码是否准确追踪了 Phase 1 数据流？可执行 PoC 是否**真的运行**并展示影响（捕获**真实输出**而非预期输出）？单元测试是否通过并演示问题？Negative PoC 是否正确识别前置条件？**是否存在人为绕过**（mocking、stubbing、禁用检查）——**有则 PoC 无效**。

#### 批量分诊

多个疑似 bug 时：先对**全部**跑 Step 0（重述常直接瓦解明显的误报）→ 逐个独立路由 → **先处理全部标准路由的，再处理深路由的** → 全部验证完后，检查**利用链**——单独未过门禁的发现可能组合成可行攻击。

#### 最终汇总格式

1. 计数：X 个 TRUE POSITIVE，Y 个 FALSE POSITIVE
2. TRUE POSITIVE 列表：每条附简要漏洞描述
3. FALSE POSITIVE 列表：每条附简要拒绝理由

## 3. 缺陷类别专项要求（9 类）

| 类别 | 关键验证点 |
|---|---|
| **内存破坏** | **先做语言安全核查**：safe Rust / 无 unsafe 的 Go / 托管语言中几乎总是误报。再查：具体破坏了什么、破坏大小与偏移是否可控、是有用原语（任意读/写、vtable 覆写）还是仅崩溃、分配器加固、UAF 的对象生命周期、类型混淆的类型不匹配证明 |
| **逻辑缺陷** | 对照 spec/RFC/设计文档而非只看代码；绘制全部状态转换（能否到达开发者未预料的状态）；识别从未被强制的隐式假设；认证缺陷要验证**全部**认证/授权路径；**逻辑缺陷会通过每一个边界检查——不要让干净静态分析说服你它是误报** |
| **竞争条件** | 实际竞争窗口是纳秒还是秒；攻击者能否扩大窗口（慢速 NFS、大分配、CPU 争用）；核验线程模型；检查全部同步原语；文件系统 TOCTOU 看符号链接竞争 |
| **整数问题** | 每点的精确类型与取值范围；有符号溢出（C/C++ 未定义行为）vs 无符号（定义为回绕）；追踪所有 cast/conversion/promotion；结果是否真用于危险用途（分配大小、数组下标、循环边界）；开 `-Wconversion`、`-Wsign-compare` |
| **加密弱点** | 对照 NIST/IETF 与已知攻击检查参数；核验随机源；nonce 重用要证明实践中确实能两次；时序侧信道要看攻击者能否触达且网络抖动是否使远程攻击不切实际；与参考实现的测试向量对比 |
| **注入** | 追攻击者输入从入口到 sink，沿途是否净化/转义；框架自动转义是否启用且未被绕过；XSS 看上下文（HTML body / 属性 / JS / URL 各需不同转义）；路径穿越看访问检查前是否规范化；测试真实 payload 经全部中间处理 |
| **信息泄露** | 具体泄露什么（栈泄露 ASLR 基址或 canary = critical；静态字符串毫无价值）；泄露数据对进一步利用是否真有用；未初始化内存要证明读点确实未初始化；时序侧信道看测量精度与噪声；错误信息是否真能到攻击者 |
| **拒绝服务** | 资源消耗比与放大是否有意义；资源可回收还是永久耗尽；**复杂度主张要证明实际最坏输入能触发，不要只声称 O(n²)**；崩溃是否可靠触发；服务是否自动重启（100ms 重启 vs 需人工介入） |
| **反序列化** | 攻击者是否确实控制到达反序列化的数据；classpath/import 图中**是否有可用 gadget 链**——没有 gadget 链只是设计异味；库与版本及已知链；类型限制/allowlist 过滤器；语言特定（Java ObjectInputStream / Python pickle / PHP unserialize / .NET BinaryFormatter） |

## 4. DSH 适配：逐条对照

已在本机 DSH 源码中核实，非推测。

### 4.1 能**原样**搬的

> ### ⚠️ 本节已更正（2026-09-19，由运行验证得出）
>
> 本节此前的结论是「**门禁机制不需要写 JS，fp-check 的 `hooks.json` 可以原样搬**」。**这条是错的。**
>
> 1. fp-check 的两个 hook 都是 `"type": "prompt"`，而 DSH **只运行 shell command 形态的 handler**。
>    实测打出的警告：`skipping unsupported "prompt" hook on Stop (only command hooks run)`
>    ——**原样搬过去一个 hook 都不会跑**。
> 2. 更关键：**DSH 的 Stop hook 拿不到对话内容**。实测 payload 只有
>    `{session_id, transcript_path:"", cwd, hook_event_name, stop_hook_active}`，`transcript_path` 恒为空。
>    所以 fp-check「扫描对话检查 6 门禁有没有走完」这一动作**在 DSH 上物理上无法实现**。
>
> **拦截本身仍然可行**：🧪 实测退出码 2 + stderr、或 `hookSpecificOutput.permissionDecision`
> 都能拦住并强制继续。但 DSH 上的门禁必须是**产物式**（检查落盘的报告 / 账本），
> 不能是**对话式**。完整实测与三个必须自己处理的坑见 `docs/dsh-stop-gate-zh.md`；
> 复现：`node tools/check-stop-gate.mjs`。

| 机制 | DSH 支持情况 | 证据 |
|---|---|---|
| 全部 Markdown 方法论内容 | ✅ 直接可用 | DSH 支持目录包与扁平 Markdown 技能 |
| **Claude Code hook 协议（含 Stop / SubagentStop）** | ✅ **原生实现** | `@deepseek-ai/dsh-hooks-claude-code` 支持 SessionStart / UserPromptSubmit / PreToolUse / PostToolUse / **Stop** / **SubagentStart** / **SubagentStop** |
| fp-check 的**强制停止门禁** | ⚠️ **可拦截，但不能原样搬**（见上方更正） | 🧪 实测：退出码 2 + stderr 即拦截，文案 `continue: blocked by Stop hook`；`SubagentStop` 则**只观测、不能阻塞** |
| 只读子代理 / 可写 PoC 代理的权限隔离 | ✅ 子代理机制齐备 | `dsh-subagent`、`subagent` / `subagent_fork` 工具 |

## 5. 落地建议

### 形态选择

| 方案 | 代码量 | 分发能力 | 适合阶段 |
|---|---|---|---|
| **A. 纯 Markdown 技能**（放 `~/.agents/skills/`） | **0 行 JS** | 仅本机 | **起步必选** |
| B. 加 hook 门禁 | ⚠️ **一个 gate 脚本（约 100–200 行）+ `configPath`**（原估「0 行 JS」已被实测推翻） | 仅本机 | A 验证有效后 |
| C. 打包成插件（`registerProvider`） | ~20–130 行 TS（**价值已上调**，见下） | npm / 市场 | 确认有价值后 |

**建议顺序：A → B → C**，不要跳级。理由：方法论的价值只能用真实审计结果来证明，包成插件只是分发手段；先包插件会把未经验证的纪律分发出去。

#### ⚠️ B 与 C 的重新权衡（2026-09-19 实测后）

| | B（command hook 门禁） | C（原生插件） |
|---|---|---|
| 看得到对话吗 | ❌ 只拿到 `cwd` + 会话 id | ✅ 在 `agent/turn-stopping` 上拿得到 `agent` 对象与会话 |
| 能做什么门禁 | 只限**产物式**（报告落盘 / 测试命令真跑过） | 产物式 **+ 对话式**（6 门禁是否真走完、13 问是否逐条答过） |
| 改动生效 | 要重启 `dsh web` | 同样要重启，但无需外部脚本 |
| 分发 | 仅本机 | npm / 市场 |

**结论**：euthyna 的门禁核心（「6 门禁有没有真走完」）属于**对话内事实**，
command hook 看不到对话 ⇒ **这条路走不通**。若门禁是项目主张的一部分，`B` 只能承担
「账目是否交齐」这类产物检查，完整门禁必须走 `C`。

> 这也意味着 **A → B → C 的中间一站 B 的价值比原先估计的低**。
> 但 A 仍然必须先做：门禁的前提是方法论本身有效，而这一点只能靠真实审计结果证明。

### 必须先决定的四件事

1. **`invocation` 策略**：`modelInvocable: true` 会让它在任何"看看这段代码"时都可能被触发；安全审计成本高（原文档自述 deep 路径约 6–8 小时），建议先设 `modelInvocable: false` + `userInvocable: true`，由你显式调用
2. **确定性引擎的边界**：定位分析结论是**不重造**调用图 / 覆盖率 / 依赖 / 密钥扫描（它们都已被占满），
   只补两件没人做的：**git 安全回归的机械判定** 与 **「符号 × 真实执行覆盖」的 join**。详见 `docs/positioning-zh.md` §7.2
3. **事实产出契约**：引擎输出什么字段、判定层消费什么字段——这是本项目真正的核心资产
4. **首次试跑目标**：建议 `D:\axe-core\axe-core` 或 dsh-mneme 的某个真实 PR，用 quick 档限定 scope，先看误报率

## 附录：DSH 技能契约速查

```yaml
---
name: code-security-audit          # 必须匹配 ^[a-z0-9]+(?:-[a-z0-9]+)*$
description: "..."                 # 触发面由它决定，写清「何时用」与「何时不用」
whenToUse: "..."                   # 可选
invocation:                        # 可选；缺省为两者皆 true
  modelInvocable: false
  userInvocable: true
---
```

- 发现路径优先级：`<项目>/.dsh/skills`(100) → `<项目>/.agents/skills`(200) → custom(300) → `~/.dsh/skills`(400) → `~/.agents/skills`(500) → bundled
- 目录包形态：`<技能名>/SKILL.md`（同级可放 `references/`、`scripts/`、`hooks/`）
- 扁平形态：单个 `.md` 文件亦可被识别
- `watch` 默认开启，Markdown 改动即时生效
- hook 支持事件：SessionStart / UserPromptSubmit / PreToolUse / PostToolUse / **Stop** / **SubagentStart** / **SubagentStop**
- ⚠️ hook **只有 `command` 形态会运行**；`prompt` / `agent` / `http` / `mcp_tool` 会被跳过。Stop hook 的 stdin **不含对话内容**
